# GradTrack Amazon S3 implementation and operations guide

This document is the handoff for GradTrack's private Amazon S3 storage integration. The application stores object keys in MySQL and generates short-lived access URLs only after GradTrack authorization. It never stores AWS credentials or presigned URLs in MySQL or frontend code.

## 1. Runtime prerequisite

The official AWS SDK version selected for this project requires **PHP 8.1 or newer**. This workstation was upgraded from PHP 8.0.30 to PHP 8.3.33 for both CLI and Apache. Composer is resolved against the application's PHP 8.1 minimum so the lock file does not accidentally select PHP 8.4-only transitive packages.

XAMPP Apache uses its CGI handler for PHP 8.3 on this workstation. This keeps PHP's current cURL/OpenSSL dependency DLLs isolated from the older DLLs bundled with Apache; CLI and web runtime probes both confirmed PHP 8.3.33 and all required extensions.

After upgrading, confirm that Apache and the CLI use the intended runtime:

```text
php --version
php -m
```

The PHP extensions used by these flows include `fileinfo`, `openssl`, `curl`, `json`, `pdo_mysql`, and `zip`. `zip` is required to inspect DOCX/XLSX/PPTX packages and reject macros or malformed Office files.

## 2. Environment configuration

Only `backend/.env` controls the active storage driver and bucket. Do not put these settings in Vite variables or frontend code. Do not commit `backend/.env`.

Development settings:

```dotenv
APP_ENV=development
STORAGE_DRIVER=s3
AWS_REGION=ap-southeast-1
S3_BUCKET=nc-gradtrack-dev-113420226807-ap-southeast-1-an
S3_PRESIGNED_URL_TTL_SECONDS=600
# AWS_PROFILE=your_gradtrack_development_profile
# AWS_SDK_LOAD_NONDEFAULT_CONFIG=1
AWS_EC2_METADATA_DISABLED=true
```

Production settings:

```dotenv
APP_ENV=production
STORAGE_DRIVER=s3
AWS_REGION=ap-southeast-1
S3_BUCKET=nc-gradtrack-prod
S3_PRESIGNED_URL_TTL_SECONDS=600
```

Production should omit `AWS_PROFILE`, `AWS_SDK_LOAD_NONDEFAULT_CONFIG`, `AWS_ACCESS_KEY_ID`, and `AWS_SECRET_ACCESS_KEY`. The EC2 IAM role supplies temporary credentials through the AWS SDK credential provider chain. Local development may use AWS IAM Identity Center/SSO, a named shared-credentials profile, or standard temporary AWS environment credentials. `AWS_PROFILE` is left for the SDK's default chain to resolve; the application does not replace the chain with hardcoded credentials.

Optional settings:

- `S3_KMS_KEY_ID`: customer-managed KMS key ARN or identifier when the bucket requires SSE-KMS.
- `S3_ENDPOINT` and `S3_USE_PATH_STYLE_ENDPOINT`: use only for a deliberate local S3-compatible emulator, never for ordinary AWS S3.
- `STORAGE_DRIVER=local`: retains the old `backend/uploads/` behavior for offline development. Production must not silently fall back to this driver.

The storage configuration contains environment guards: production accepts only `nc-gradtrack-prod`, and every non-production S3 environment accepts only `nc-gradtrack-dev-113420226807-ap-southeast-1-an`.

## 3. Implemented storage architecture

The PHP backend is the only application component that communicates with S3. The initial upload path is:

```text
Browser -> authenticated PHP API -> entity/role authorization -> server validation
        -> UUID object key -> private S3 upload -> MySQL object-key reference
        -> authorized application response
```

The database stores the object key, original filename, MIME type, byte size, category-specific metadata, uploader/owner relationship, and timestamps where the existing schema supports them. It does not store the bucket, Region, AWS credentials, permanent S3 URLs, or presigned URLs.

The centralized adapter is `backend/api/config/storage.php`. It provides:

- environment validation and the standard AWS credential provider chain;
- UUID v4 object names and normalized object keys;
- local/S3 upload, metadata/head, existence, copy, and deletion operations;
- SHA-256 metadata and S3 checksum submission;
- short-lived presigned GET URLs with safe content disposition;
- compatibility with existing `uploads/...` database references;
- generic client errors and server-side logs that do not expose credentials;
- cleanup helpers for compensating transactions.

All S3 objects remain private. Media that is viewable to a signed-in or public-site visitor is still retrieved through a short-lived URL generated by GradTrack. Chat, supporting documents, mentor proof, job requirements, and reports remain protected by application authorization.

```text
  announcements/{announcementId}/cover/{uuid}.{ext}
  announcements/{announcementId}/gallery/{uuid}.{ext}
  public-content/about/{contentId}/{uuid}.{ext}

private/
  chat/rooms/{roomId}/attachments/{uuid}.{ext}
  graduate-documents/{accountId}/{documentType}/{uuid}.{ext}
  mentorship/proofs/{accountId}/{uuid}.{ext}
  job-support/job-posts/{jobId}/requirements/{uuid}.{ext}

staging/
  chat/rooms/{roomId}/{uuid}.{ext}
  system-branding/{imageType}/{uuid}.{ext}
  imports/graduate-master/{importJobId}/{uuid}.xlsx        (reserved)

  exports/{module}/{exportJobId}/{uuid}.{ext}               (reserved)
```

S3 has object keys, not real directories. Console folders are only zero-byte placeholder keys and prefixes. Existing `media/`, `private/`, `staging/`, `system/`, and `temporary/` placeholders are harmless; application uploads create nested prefixes automatically.

## 5. Feature behavior

| Feature | S3 key/policy | Access and retention |
|---|---|---|
| Admin profile | `media/profiles/admins/...` | Private object; presigned view; replace after DB commit |
| Graduate profile/cover | `media/profiles/graduates/...` | Private object; presigned view; replace/remove after commit |
| Forum images/videos | `media/community-forum/posts/...` | Private object; presigned display; multiple media records; one physical object per upload |
| Announcement cover/gallery | `media/announcements/...` | Private object; presigned display; draft media is never anonymously public S3 content |
| About-page admin uploads | `media/public-content/about/...` | Private object; presigned display; bundled frontend defaults remain build assets |
| Branding | stage, then `system/branding/...` | Two-step upload promoted on settings save; abandoned staging is lifecycle-cleaned |
| Chat attachment | stage, then `private/chat/...` | Room membership required; images/PDF may be inline; documents force download |
| Graduate document | `private/graduate-documents/...` | Owner authorization; short-lived download |
| Mentor proof | `private/mentorship/proofs/...` | Owner-only management; never public |
| Job requirement | `private/job-support/...` | Authenticated graduate access; metadata stored in `job_posts` |
| Graduate master import | No S3 in current synchronous flow | Browser parses XLS/XLSX and backend validates submitted records; source is not retained |
| Alumni registry import | No S3 in current synchronous flow | Browser parses CSV/XLSX and backend batch-validates rows; source is not retained |
| Existing synchronous exports | Direct response/download | PDF, Excel, CSV, survey, alumni, audit, and GenAI exports are not stored unnecessarily |
| Future large async export | `temporary/exports/...` | Use only when an export job is asynchronous/retryable; expire automatically |
| SQL/RDS backup | Not handled by S3 feature code | Use RDS automated backups, snapshots, or AWS Backup |

The two current imports do not send the physical spreadsheet to PHP. Uploading their PII source files to S3 would add retention risk without improving the current synchronous workflow. If either import becomes asynchronous, add an import-job record and use the reserved staging prefixes, delete successful sources within seven days, and retain failed sources no longer than thirty days with an approved operational reason.

## 6. Chat attachment lifecycle

1. A graduate selects one attachment. The current UI intentionally remains single-attachment-per-send.
2. PHP authenticates the graduate, checks room membership, validates the file, and uploads it under `staging/chat/rooms/{roomId}/...`.
3. MySQL stores the pending attachment row with `message_id` null, uploader, original name, UUID stored name, object key, MIME type, size, and attachment type.
4. When the message is saved, the backend rechecks ownership, copies the object to `private/chat/rooms/{roomId}/attachments/...`, updates the row in the same message transaction, commits, and removes the staging object.
5. Socket.IO publishes the normal message/attachment record. It never receives AWS credentials or a permanent S3 URL.
6. Opening an attachment calls the GradTrack attachment endpoint. The endpoint checks authentication, room membership, and the attachment/message relationship, then redirects to a short-lived presigned GET URL.
7. JPG, PNG, WebP, and PDF may use inline disposition. DOCX, XLSX, PPTX, TXT, and CSV always use attachment/download disposition.
8. If promotion or the database transaction fails, newly copied objects are removed. Unlinked staging objects are also covered by lifecycle expiration.

The schema can represent multiple attachment rows even though the present UI sends one at a time. Message retry/idempotency behavior is preserved through the existing client message identifier.

## 7. File validation baseline

Validation happens in PHP and does not trust the browser MIME value. All stored object names are UUIDs; original names are sanitized and kept only as metadata/download names.

| Category | Allowed content | Limit |
|---|---|---|
| Profile, cover, announcement | JPG/JPEG, PNG, WebP, GIF | 5 MB; maximum 8192 px per side |
| About-page image | JPG/JPEG, PNG, WebP | 4 MB; maximum 8192 px per side |
| Branding | PNG, JPG/JPEG, WebP, GIF; ICO only for favicon | 2 MB, or 5 MB for login background; maximum 8192 px per side |
| Forum image | JPG/JPEG, PNG, WebP, GIF | 5 MB; maximum 8192 px per side |
| Forum video | MP4, WebM, OGV, MOV | 50 MB |
| Chat image | JPG/JPEG, PNG, WebP | configurable, default 10 MB; maximum 8192 px per side |
| Chat document | PDF, DOCX, XLSX, PPTX, TXT, CSV | configurable, default 25 MB |
| Graduate document | PDF, JPG/JPEG, PNG, DOCX | 5 MB; safe image dimensions; DOCX package inspection |
| Mentor proof | JPG/JPEG, PNG, WebP, PDF | 5 MB; safe image dimensions |
| Job requirement | PDF, DOCX, JPG/JPEG, PNG | 10 MB; safe image dimensions; DOCX package inspection |

Controls include upload status, non-empty size, `is_uploaded_file`, `finfo` MIME detection, extension/MIME agreement, safe image decoding and dimensions, UUID naming, dangerous/double-extension rejection, entity authorization, and Office ZIP structure/macro checks. Executables, scripts, HTML, JavaScript, SVG, legacy macro-capable Office formats, macro-enabled packages, and ZIP uploads are not accepted.

Malware scanning is not included in this codebase. Before increasing upload scope or allowing external documents at larger scale, add a quarantine/scan status and an event-driven malware scanner (for example, S3 event -> scanning service -> tagged clean object). Do not make an unscanned object available when such a policy is enabled.

## 8. Database migration

Review `database/add_s3_storage_metadata.sql`. It adds only the nullable job-requirement metadata fields that were previously held in local `metadata.json` files:

- `requirements_file_path`
- `requirements_file_name`
- `requirements_mime_type`
- `requirements_file_size_bytes`
- `requirements_uploaded_at`

The application does not automatically add these S3-related columns during an ordinary request. Run the migration against a backed-up development database first. Do not execute it in production without explicit approval and a maintenance/rollback plan.

Existing `file_path` and `storage_path` fields continue to store either an old `uploads/...` path or a new S3 object key. This avoids a broad schema redesign.

## 9. Existing-file migration

No existing local file is automatically moved or deleted.

First backfill legacy job `metadata.json` records into the new MySQL fields:

```text
php backend/scripts/backfill_job_requirement_metadata.php
php backend/scripts/backfill_job_requirement_metadata.php --apply --confirmed-synthetic-data-only
```

The first command is a dry run. The second is allowed only for verified synthetic development data. A manifest is created in `backend/tmp/`. Roll back database changes with:

```text
php backend/scripts/backfill_job_requirement_metadata.php --rollback=path-to-manifest.json
```

Then audit all legacy references:

```text
php backend/scripts/migrate_legacy_uploads_to_s3.php
```

The dry run:

- enumerates known database file fields;
- matches references to files under `backend/uploads/`;
- calculates SHA-256 checksums;
- maps records to module-specific S3 keys;
- reports missing and orphaned files;
- deduplicates identical legacy paths, including duplicated old forum references;
- writes a manifest without uploading or updating MySQL.

After reviewing the manifest, the development apply command is:

```text
php backend/scripts/migrate_legacy_uploads_to_s3.php --apply --confirmed-synthetic-data-only
```

For a reviewed development dataset that is not synthetic, use `--confirmed-development-data`. A single module can be migrated with `--kind=<kind>`. For example, the chat-only workflow is:

```text
php backend/scripts/migrate_legacy_uploads_to_s3.php --kind=chat-attachment --manifest=backend/tmp/chat-dry-run.json
php backend/scripts/migrate_legacy_uploads_to_s3.php --apply --confirmed-development-data --kind=chat-attachment --manifest=backend/tmp/chat-applied.json
```

Global orphan detection is intentionally skipped for a scoped migration because references owned by out-of-scope modules have not been inventoried.

It uploads, verifies S3 metadata/checksum, then updates the matching database reference. If the database update fails, the newly uploaded object is removed. Rollback restores old database references and retains both S3 and local files:

```text
php backend/scripts/migrate_legacy_uploads_to_s3.php --verify=path-to-applied-manifest.json
php backend/scripts/migrate_legacy_uploads_to_s3.php --rollback=path-to-manifest.json
```

Verification is read-only: it compares the current database value with the manifest, confirms `HeadObject` metadata, downloads and hashes the S3 content, generates a private presigned URL, and confirms the original local backup remains readable.

Production tools additionally require `--production-approved`, but that flag must not be used until an explicit production migration approval is given. Keep the local files as a backup until every record, view, download, permission boundary, and checksum has been verified. Local deletion is a separate later operation and is not implemented by these tools.

## 12. Manual S3 console settings

For both buckets:

1. Keep Object Ownership as **Bucket owner enforced / ACLs disabled**.
2. Keep all four **Block Public Access** controls enabled.
3. Keep objects private; do not add a public-read bucket policy or public ACL.
4. Enable default encryption. SSE-S3 is sufficient for the initial deployment; use a customer-managed KMS key only when the college has a key-ownership/audit requirement and accepts the additional permissions and cost.
5. Keep the Region at `ap-southeast-1`, matching the current architecture and reducing cross-region transfer/latency.
6. S3 CORS is not required for backend-mediated uploads and presigned GET redirects. Add CORS only if a later design deliberately uses browser-to-S3 upload.
7. Consider versioning enabled in production for recovery. Development may keep it disabled to reduce cost. If versioning is enabled, add noncurrent-version lifecycle cleanup.
8. Consider CloudTrail data events for sensitive-object audit requirements. S3 server access logging is optional and needs a separate dedicated log bucket; do not write access logs into the same data bucket.
9. Optionally add a bucket policy that denies requests when `aws:SecureTransport` is false. Preserve Block Public Access and test the role after applying it.

Recommended lifecycle rules:

| Prefix | Expiration |
|---|---|
| `temporary/diagnostics/` | 1 day |
| `temporary/exports/` | 7 days |
| `temporary/failed-uploads/` | 7 days |
| `staging/system-branding/` | 2 days |
| `staging/chat/` | 7 days |
| `staging/imports/` | 7 days by default; failed imports up to 30 days only with a separate tag/rule |
| Incomplete multipart uploads | Abort after 1 day |
| Noncurrent versions, if versioning is enabled | Delete after 30 days after confirming recovery requirements |

Do **not** add automatic expiration to `media/`, `private/`, or `system/`. Their deletion is driven by GradTrack replacement/deletion logic and database ownership. Expiring them independently would leave broken database references.

## 14. Production deployment checklist

Production deployment remains unapproved. After development passes and explicit approval is given:

1. Back up the production database and inventory `backend/uploads/` without changing it.
2. Upgrade the production PHP runtime to 8.1+ and confirm required extensions.
3. Attach the production least-privilege S3 policy to the EC2 role; do not create permanent application access keys.
4. Review bucket encryption, Block Public Access, Object Ownership, versioning, lifecycle, and logging.
5. Deploy source and run `composer install --no-dev --prefer-dist --optimize-autoloader`.
6. Set the production environment values shown above; ensure no development bucket/profile is present.
7. Review and execute the database migration during the approved change window.
8. Smoke-test authentication and legacy local-file reads while still retaining local files.
9. Pilot new uploads with non-sensitive test content, then verify S3 metadata, DB key, access control, replacement, and deletion.
10. Dry-run both migration utilities and review missing/orphaned/deduplicated records.
11. Apply the legacy migration only after separate explicit approval.
12. Monitor PHP/S3 errors, CloudTrail or access logs, S3 request counts, storage growth, and lifecycle cleanup.
13. Remove old local files only in a later approved cleanup after backups and full verification.

## 15. Failure and cleanup behavior

- S3 failure: no active database reference is created.
- S3 success/database failure: the new object is deleted through compensating cleanup.
- Replacement: the new database reference commits before the old object is deleted.
- Delete failure: the database operation remains authoritative and the storage error is logged for reconciliation; no bucket-wide or recursive destructive operation is attempted.
- Chat promotion failure: copied destination objects are removed and the message transaction rolls back.
- Missing object: the API returns no usable access reference or the protected endpoint produces a neutral not-found response.
- Expired URL: the frontend requests the GradTrack API again to obtain a newly authorized short-lived URL; URLs are never refreshed from database values.
- Interrupted upload: the PHP request fails without creating an active row; staging lifecycle and incomplete-multipart cleanup provide a second safety net.

Periodic reconciliation should compare active MySQL references with S3 Inventory or a scoped prefix listing, report missing references and orphan objects, and delete orphans only after review. Never infer ownership from an original filename.

## 16. Cost controls

- Enforce the current upload limits, particularly forum videos and chat documents.
- Keep synchronous exports direct instead of creating duplicate S3 objects.
- Expire staging, diagnostics, failed uploads, and future temporary exports.
- Do not retain import source files containing PII without a documented need.
- Apply noncurrent-version cleanup when versioning is enabled.
- Avoid duplicate forum objects and preserve one database reference per physical upload.
- Monitor S3 Storage Lens/CloudWatch metrics and configure an AWS Budget alert.
- Use CloudFront later only when public-viewable media traffic justifies it; CloudFront must use private-origin access, not public S3 objects.

## 17. Deliberate limitations

- Live development-bucket S3 write/read/delete integration and authenticated HTTP upload flows have been verified. Production was not contacted.
- No production bucket call, production database migration, production upload, or existing-file deletion was performed.
- Current imports remain synchronous and do not stage source files in S3.
- Current small exports remain direct downloads; the reserved temporary export prefix is not used yet.
- Malware scanning and a persistent deletion-retry queue are not part of the current schema. Failures are logged and must be reconciled operationally.
- Company logos, job-post images, resumes/job applications, comment attachments, and other features not present in the existing product were not invented.
